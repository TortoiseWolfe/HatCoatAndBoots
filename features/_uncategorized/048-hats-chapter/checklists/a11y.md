# Checklist: Accessibility & Graceful Degradation — Requirements Quality

**Purpose**: Unit-test the _requirements_ (not the implementation) for the chapter's accessibility, no-JS fallback, reduced-motion, keyboard, and progressive-enhancement coverage. Each item asks whether the spec is complete, clear, consistent, and measurable on these dimensions.
**Created**: 2026-05-30
**Feature**: [spec.md](../spec.md) · **Focus**: a11y + graceful degradation (the Hat/Coat constitution gates)
**Depth**: Standard · **Audience**: Reviewer (PR) + spec author

## Requirement Completeness

- [ ] CHK001 - Are no-JS fallback requirements defined for _every_ interactive control (toggles, guided views, chapter focus, prev/next nav), not just the diagram? [Completeness, Spec §FR-008]
- [ ] CHK002 - Are screen-reader announcement requirements specified for _both_ control state changes _and_ the explanation/description updates? [Completeness, Spec §FR-011]
- [ ] CHK003 - Is the skip-link requirement specified (target, placement, visibility-on-focus)? [Completeness, Spec §FR-010]
- [ ] CHK004 - Are requirements defined for the focus indicator's visibility (not just "visible focus" but discernible against the panel/parchment background)? [Gap, Spec §FR-010]
- [ ] CHK005 - Are print requirements defined beyond "shows the drawing + text" (e.g., are inert controls hidden or shown in print)? [Gap, Spec §Edge Cases]
- [ ] CHK006 - Is a text alternative requirement defined for the diagram as a whole (so a screen-reader user gets the lesson), distinct from per-element alt text? [Gap, Spec §FR-001 / Key Entities: Drawing Element]

## Requirement Clarity

- [ ] CHK007 - Is "operable by keyboard alone" decomposed into specific, testable behaviors (Tab into groups, arrow within group, Space/Enter to activate)? [Clarity, Spec §FR-010]
- [ ] CHK008 - Is the colorblind distinction requirement for the two suns quantified beyond "more than color" (which specific non-color cues — shape, angle, label)? [Clarity, Spec §FR-012]
- [ ] CHK009 - Are the _two_ reduced-motion triggers (OS/browser preference AND the app's own setting) each named unambiguously so both are testable? [Clarity, Spec §FR-013]
- [ ] CHK010 - Is "controls are present but inert rather than broken" (no-JS) defined with observable criteria — what does "inert" look like vs "broken"? [Clarity, Spec §FR-008 / US3 AS-1]
- [ ] CHK011 - Is the aria-live politeness level for the explanation specified (polite vs assertive), or left ambiguous? [Ambiguity, Spec §FR-011]

## Requirement Consistency

- [ ] CHK012 - Do the 44×44 px touch-target requirement (FR-014) and the keyboard-operability requirement (FR-010) consistently apply to the _same_ full set of controls (toggles + views + focus + nav + language stub)? [Consistency, Spec §FR-010/§FR-014]
- [ ] CHK013 - Is the no-JS "complete composite visible" requirement (FR-008/SC-002) consistent with the toggle requirement that hidden elements use opacity-not-display (FR-006) — i.e., does the spec make clear the SSR state shows all layers? [Consistency, Spec §FR-006/§FR-008]
- [ ] CHK014 - Are the a11y requirements stated for the Hat page consistently applied to the Coat/Boots coming-soon focuses (same shared viewer)? [Consistency, Spec §FR-007/§FR-007b]

## Acceptance Criteria Quality

- [ ] CHK015 - Is "zero WCAG 2.1 AA violations in automated testing" tied to a named tool/standard so it is objectively verifiable? [Measurability, Spec §SC-003]
- [ ] CHK016 - Is the "in under 2 minutes, without instruction" success criterion measurable and attributable to the a11y/guided-view design rather than subjective? [Measurability, Spec §SC-001]
- [ ] CHK017 - Can "100% of the lesson visible with scripts disabled" (SC-002) be objectively checked against a concrete enumerated list of lesson elements? [Measurability, Spec §SC-002]
- [ ] CHK018 - Is the phone-viewport single-column reflow (SC-006) defined with a breakpoint or width threshold, or left as "narrow"? [Clarity, Spec §SC-006/§FR-014]

## Scenario & Edge-Case Coverage

- [ ] CHK019 - Are requirements defined for the _pre-hydration_ window (scripts loading but not ready), distinct from the _no-JS_ case? [Coverage, Spec §Edge Cases: pre-interactive]
- [ ] CHK020 - Are requirements defined for the empty-drawing state (all elements toggled off) being announced/recoverable for assistive tech, not just visually stable? [Coverage, Spec §Edge Cases: empty drawing]
- [ ] CHK021 - Are recovery requirements defined when the self-hosted font fails to load (fallback legibility), and is that stated as an a11y/legibility guarantee? [Coverage/Exception, Spec §FR-013a]
- [ ] CHK022 - Are requirements defined for how a screen-reader user perceives a "custom" (non-preset) state vs a named view? [Gap, Spec §FR-005]
- [ ] CHK023 - Is the reduced-motion path defined as _no animated transition_ (instant swap) rather than merely "shorter", so it's unambiguous? [Clarity, Spec §FR-013/§US3 AS-5]

## Traceability & Definitions

- [ ] CHK024 - Does each accessibility FR map to at least one measurable success criterion (FR-010/011/012/013/014 ↔ SC-003/SC-006)? [Traceability]
- [ ] CHK025 - Is "assistive technology" scoped (screen readers at minimum) so "expose name and state" is testable? [Clarity, Spec §FR-011]
